# 栖语 Dream 深度重组间隔调整为 3 天

Status: ready-for-agent

本 Spec 依据 2026-08-24 讨论与需求制定：将栖语记忆体系中第五动作 Dream（深度重组）的执行最小间隔由原先保守默认的 7 天调整为 3 天一次。人格底色与核心记忆设计继续以 `E:\Note\Agent\栖语\栖语产品灵魂.md`、`栖语system prompt\人格宪法.md`、`栖语记忆\Dream.md` 为准。

## Problem Statement

栖语的 Dream（深度重组）负责从日常积累的互动证据中提炼高层长期印象（`long-memory.md`）并对 PersonaTree 根节点进行升降与清理。在原定稿设计中，Dream 最小执行间隔取了保守值 7 天（每周一次）。

然而在实际使用中，7 天的周期偏长：用户在几天内的生活变迁、重要事件和阶段性状态变化，需要等待整整一周才能被 Dream 识别并提炼到长期印象中，导致长期记忆的沉淀存在较长滞后。

用户希望将 Dream 最小间隔缩短至 **3 天一次**，使得关系理解与长期印象能够更敏锐、适时地反映近期的生活状态，同时仍保持异步离线、晚安后触发和严格自检的防漂移机制。

## Solution

将 Dream 服务的最小日历日差判定标准由 7 天变更为 3 天：

1. **资格判定**：
   - 触发时机仍保持仅限用户明确晚安（睡前收束完成）后，或上次未成功留下的待补跑请求（pending）；
   - 距上次成功执行 Dream 的本地日历日差必须 $\ge 3$ 天（从未成功执行过视为满足）；
   - 距上次成功 $< 3$ 天时，晚安触发将被静默拦截（返回 `notDue`），模型绝不被调用；
   - 满 3 天后，晚安触发正常组装素材并调用模型进行深度重组。

2. **状态与诊断**：
   - 开发者诊断接口上报的 `minIntervalDays` 更新为 3；
   - 诊断事实中的 `intervalSatisfied` 判定与核心资格复查使用完全一致的 3 天判定口径。

3. **安全与不变性**：
   - 每日日终归档和新月月压缩每天正常独立运行，绝不重置或绕过 3 天间隔；
   - 草稿四关自检（预算、格式、脱敏、证据与用户控制）与静默原子接纳机制保持不变；
   - 未配置 Provider 时不运行，绝不用本地规则胡乱生成长期记忆；
   - 记忆控制（冻结、禁提、删除）依然在 3 天周期的重组中拥有最高优先级。

## User Stories

1. 作为用户，我希望在上次 Dream 过去 3 天后说晚安时触发新的深度重组，以便我近几天的重要经历与状态更快进入长期记忆。
2. 作为用户，我希望在距上次 Dream 成功不足 3 天（如 1 天或 2 天）时说晚安不会触发 Dream，防止长期记忆过于频繁刷新而发生语义漂移。
3. 作为用户，我希望每天的日终归档照常执行，并且日终归档绝不会提前重置或绕过 3 天的 Dream 间隔。
4. 作为用户，我希望从未使用过 Dream 时，第一次说晚安能够直接具备执行资格并完成首次深度重组。
5. 作为用户，我希望当晚因网络超时或关闭应用导致 Dream 未成功时，下次启动且满足 3 天条件时能自动补跑。
6. 作为用户，我希望在未配置 LLM 时即使间隔已满 3 天也不会执行 Dream，防止用机械规则污染长期记忆。
7. 作为用户，我希望 Dream 依然在后台异步静默完成并自动采用，不需要在聊天中向我弹窗确认或征求批准。
8. 作为用户，我希望在设置页的开发者诊断视图中看到当前 Dream 的最小间隔为 3 天。
9. 作为用户，我希望在开发者诊断中准确看到当前距上次成功的日历天数以及「当前是否满足间隔」的真实状态。
10. 作为用户，我希望 3 天周期的 Dream 仍严格遵守热层预算（2000-3000 tokens），超出时自动将细节下沉至 episodes。
11. 作为用户，我希望 3 天周期的 Dream 依然严格执行证据核对，未在已归档日摘要中出现的事实绝不写入长期记忆。
12. 作为用户，我希望被我纠正、禁提或删除的内容在 3 天周期的 Dream 中绝不复活。
13. 作为用户，我希望被我冻结的画像节点或长期记忆条目在 3 天周期的 Dream 中原样保留，不得被修改或删除。
14. 作为用户，我希望 3 天周期的 Dream 在替换长期记忆前依然自动生成备份文件，以便在异常时可完整回滚。
15. 作为用户，我希望 3 天间隔的计算基于本地自然日历日差（例如 8月15日成功后，8月18日即算作满 3 天），行为清晰且符合直觉。

## Implementation Decisions

1. **常量与判断口径统一**：
   - 核心服务中的最小间隔常量统一设定为 3 天。
   - 晚安预登记标记（`markBedtime`）、正式执行资格检查（`run`）和开发者诊断事实（`healthFacts`）全部基于此常量进行 `daysSinceLastSuccess >= 3` 的判定。

2. **诊断与 API 数据结构不变**：
   - 诊断 JSON 负载中的 `minIntervalDays` 字段输出为 `3`。
   - 前端无需修改解析逻辑，自动动态展示 `最小间隔 3 天`。

3. **保留全部已有可靠性与安全设计**：
   - 维持全量候选草稿与 `changes.md` 诊断清单机制；
   - 维持四关自检与失败整份作废原则；
   - 维持单段备份与 history 归档留存；
   - 维持非阻塞首响原则（Dream 永远在可见回复交付后异步触发）。

## Testing Decisions

1. **测试标准**：
   - 测试必须针对模块外部可观察行为（返回值状态、落盘文件内容、模型调用次数、诊断数据），不耦合私有实现细节。
   - 测试必须覆盖：
     - 初始状态资格满足；
     - 间隔内（1天、2天）被拦截为 `notDue`，且模型不发生网络调用；
     - 满 3 天（正好 3 天）晚安触发成功接纳为 `accepted`，且模型被调用并正确生成新长期记忆；
     - 日终归档连续执行后不破坏间隔阻拦；
     - 开发者诊断在 2 天前成功时显示 `intervalSatisfied: false`，在 3 天前成功时显示 `intervalSatisfied: true`。

2. **模块覆盖与参考既有测试**：
   - 针对 Dream 服务的单元测试；
   - 针对开发者诊断服务的单元测试；
   - 针对前端诊断客户端与界面的 Mock 测试。

## Out of Scope

1. 修改随手记（每 4-6 轮）、日终归档（每日/晚安/启动）或月压缩（新月）的触发时机与逻辑。
2. 在 UI 设置中增加用户自由输入 Dream 间隔数字的设置表单（保持作为系统行为常数）。
3. 调整 Dream 的 prompt 模板、长期记忆分区或 PersonaTree 根节点升级判定跨度（如性格 7 天跨度保持独立定稿）。
