# 语音档位映射与千问朗读档的地址派形状

本 ADR 记录语音档位映射专题（spec `.scratch/voice-tier-mapping/spec.md`，实现决策第 4、5、9 条）的首个决定：**qwen_tts 档按地址派形状**接入千问 3.1 朗读——地址主机含 `maas.aliyuncs.com` 走官方新版 SpeechSynthesizer 端点（CosyVoice 家族请求体），否则走现行 multimodal 形状；首版只接整段路径。与 ADR 0014（自定义档边界与下载跳）、ADR 0015（模型与接口不匹配）、ADR 0018/0019（流式交付）同族；映射表边界见文末（票 03 补节）。

## Context & Decision

1. **qwen_tts 档地址派形状。** 千问 3.1 语音型号整体迁到要拼业务空间 ID 的新域名（`https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/services/audio/tts/SpeechSynthesizer`），请求体也从 multimodal 家族换到 CosyVoice 家族（`model` + `input{text, voice, format, sample_rate}`，官方文档与前置实测核实）。分派判定：**地址主机含 `maas.aliyuncs.com` 走 3.1 新形状，否则走现行 multimodal 形状**。只看主机（大小写不敏感，端口与路径不影响），只在 Host 网关层（`qwen_tts_gateway.dart`）——不进配置字段、不进服务层与 UI。先例：千问识别档按地址路径里是否带 `/compatible-mode/` 唯一确定形状——一个档内两种地址长相，用户不需要理解两种协议。非 2xx 照旧走统一分类（ADR 0015 的 `modelInterfaceMismatch` 判定不因形状分派而漂移）。

2. **不加独立档位、不引入占位符语法。** 用户把官方地址里的 `{WorkspaceId}` 替换成自己的业务空间 ID 后**整条填入**地址栏，Host 不代填、不做模板拼接、不开「官方 3.1」新档位。理由：业务空间 ID 是用户自有资产，代填意味着 Host 要多存一份或多开一个地址字段；独立档位会把同一个千问服务拆成两份配置，凭据作用域、缺省值与设置页说明全部翻倍，而两种形状的分派判定一句话就能说清。设置页只给官方地址模板与拼接指引。

3. **首版只接整段，流式待补（前置实测裁定）。** 3.1 SSE 逐块形状无法实测——聚合站 Key 在业务空间校验层即被拒（HTTP 400 `BadRequest.IllegalEndpoint`，鉴权层未到达），无任何可用 3.1 通路；按异构处理，不赌 SSE 与现款同构。3.1 新形状上流式接口按 E1 降级：每句走一次整段合成、收成一个完整容器块，分句层照常按句等整段返回（宁可慢一点也不出坏声音）。首块要等合成 POST 与下载跳两跳串行才到，降级路径**不套**流式收口的外层空闲计时（那是从订阅起算的块间空闲预算，按单跳 60 秒计时会把合法慢两跳如 40s+40s 在第 60 秒砍掉）——两跳各自的 60 秒预算与异常分类已在出网调用与下载通道内生效，单跳卡死仍按单跳预算报超时。设置页型号说明如实标注「流式待补」，缺口不静默。将来拿到自有业务空间 Key 后，以实测留存的现行 SSE 对照基线逐块比对再接真流式，接口面不需要变。

4. **新形状走既有下载跳（ADR 0014 语义不变）。** 非流式响应的 `output.audio.url` 与现行形状同路径，提取共用一份；音频地址经 `downloadSpeechAudioBytes` 取回——http/https 限定、同一套 SSRF 内网校验、不带鉴权头（getBytes 无 headers 形参的结构性决定）、不跟重定向、单跳同级超时预算（60 秒）、内存即焚。服务端返回的地址同样受内网约束，新端点不带来新的出网缺口。

5. **高级参数按既有千问档合并语义适配新形状。** `extraParams` 深合并进 `input`：官方新增字段（如 CosyVoice 的 `instruction`）由此透传，用户显式写的 `format`/`sample_rate` 覆盖协议缺省（缺省 `wav`/24000）。音色空缺回落本家族官方示例音色（`longanhuan_v3.6`，与现行形状回落 `Cherry` 同律，各按各家族的官方示例）。

6. **可达性如实标注。** 前置实测（probe 01，2026-09-24）判定聚合站 Key 对 maas 新域名不可用，3.1 接入需自有阿里云百炼业务空间 ID 与自有百炼 Key。设置页千问朗读档型号说明给官方地址模板与业务空间 ID 拼接指引，如实标注 Key 要求与「流式待补」；聚合站域名不进代码与文档（spec 决策 9）。

## Consequences

- qwen_tts 一个档覆盖千问新旧两代朗读端点：用户上 3.1 只改地址与型号两栏；换地址不沿用旧 Key 的既有凭据机制照旧工作。
- 分派判定一处实现、既有 multimodal 路径的行为、解析与测试用例逐字不动，回归面收敛在新增分支。
- 3.1 用户的聊天页朗读节奏从「边出文字边出声」退到「按句等整段返回」——异构假设下的保守取舍，设置页已如实标注；实测通路复活后在同一条 E1 降级路径上启用真流式即可，不需要新接口。
- 试听、历史重听、连接测试在新形状上端到端可通（连接测试＝真实试听，与现行千问档同口径）；真 Key 冒烟留交付后真机流程。

## 映射表边界（票 03 补节）

映射表是随包内置的常量数据表＋查询纯函数，落在 Host 包（`voice_tier_mapping.dart`），收千问语音族：qwen3-tts/asr 现行型号、qwen-audio-3.x 各型号、realtime 系（含 3.1 五型号）；豆包型号暂不收。三个边界决定：

1. **数据随发版更新，不做运行时拉取。** 新模型发版＝加一行数据随版本发布，与 LiteLLM 等业界集中映射表的维护方式同律。明确不做运行时从远端拉取：表决定请求打向哪个端点与档位，表一旦可被远端替换，篡改表即等于把请求与本机密钥指到攻击者的地址——这是「密钥不出本机」架构的一部分，不是功能取舍。同理不做用户自填映射：自填等于让用户手工写协议路由，错一行就是静默打错协议，建议面交给官方文档与引导话术。
2. **名字推断只保留型号驱动的受限规则。** 档内 `-realtime` 后缀规则（`isQwenRealtimeTtsModel`，ADR 0018）照旧；不做开放式的「按模型名字符串猜协议」——名字没有权威命名空间，同前缀可对应多协议（千问正是如此），推错比报错代价高（行业调研结论，spec 问题陈述）。表里查不到的型号一律返回未知、行为一字不变：ADR 0015 的 `-realtime` 判定、「模型与接口不匹配」分类与文案、可区分错误码、client 类别全部逐字保留；表命中只升级文案内容，不新增事件种类与错误码。
3. **单一真相在 Host，表只建议不拦截。** 浏览器侧只消费连接测试结果里的结构化建议字段（`suggestion`），不复制表、不做双源同步。连接测试在发出任何请求前查表，命中「应换档／不支持」直接返回建议、零出网；保存设置不查表不拦截——映射表不是出网闸门，用户用聚合站等替代上游时自己的填法原样保留。新版端点（含业务空间 ID）只给官方地址模板与拼接指引、不代填；跨档回填会把官方地址模板整条填进地址栏作草稿，未替换的 `{业务空间ID}` 占位含中文，由既有地址校验（可见 ASCII 脏字符拦截）人话驳回，不会被原样保存或出网。一键换档回填走确认制，跨档沿用「切换服务不沿用旧 Key」既有凭据机制。
