# 上游「url error」拒绝识别为模型与接口不匹配

语音出网请求里有一类失败：用户选的型号本身存在、Key 有效、请求体形状正确，服务端仍以 400 拒绝，只因该型号落在另一套 API 家族（流式或异步型号打到本 Host 只会用的 HTTP 内联端点）。本 ADR 记录把这类失败从通用拒绝里分出的决定：新增失败种类 `modelInterfaceMismatch`，判定放在出网非 2xx 的统一分类函数一处，连接测试与正式转写/合成给同一句可定位人话。与 ADR 0001（Host 中介）、ADR 0007（接口异常分类与文案）同族。

## Context & Decision

1. **判定依据：两个诊断实录的真实案例。** 千问语音合成填 `qwen-audio-3.1-tts-next`（WebSocket 流式合成型号）、千问语音识别填 `qwen-audio-3.0-asr-flash-filetrans`（异步文件转写型号），两者打到 HTTP 内联端点，服务端一律回 400 `InvalidParameter: url error`。对照组同 Key、同端点、同请求体形状换 `qwen3-tts-flash` / `qwen3-asr-flash` 全部 200；同端点发不存在的模型名回的是另一种错误（`Model not exist.`）。即端点、Key、请求体字段全部正确，唯一变量是模型名与接口家族的匹配关系。用户侧恢复动作是换型号（两个 App 缺省值即可用），因此提示话术指向「更换模型或调整服务地址」两个动作。

2. **判定放在 `providerStatusFailure` 一处。** 该函数是全部出网 HTTP 非 2xx 的统一分类入口：聊天模型、语音转写（OpenAI 兼容/千问/豆包/自定义）、语音合成（各协议档）、音频下载跳等带响应体的通道都经它出分类（联网搜索传空响应体，关键词分支不触发）。新种类在这里落地后，经 `providerTestStatusFromFailureKind` 与 stt/tts 两张错误码表自然流到三处连接测试与正式转写/合成路径，各协议网关零改动，也不会出现同一错误在各网关分类不一致。判定顺序沿用既有嗅探模式：401/403、429、找不到模型之后，通用兜底之前；4xx 且响应体小写化后含 `url error` 即归入新种类。

3. **允许列表只认 `url error` 一个关键词。** 取舍是宁可漏判也不误判：普通 400（参数错、鉴权头形态错等）保持通用 provider 分类与文案不变，只有诊断实证过的这一个连续子串触发新种类。DashScope 该错误的 message 里带帮助链接 `error-code#error-url`，链接形态不含连续子串「url error」，不会误命中；真实响应体整条命中判定有测试锁定。给后来者的判据：走网关代理的服务若把「url error」写进中间层自产文案（如转发失败提示），会误命中本分支——区分看响应体出自上游服务端本身还是中间层；真命中时用户换型号或调服务地址即可解决，误命中不能，此类形态的修法是改精确判定（如限定 JSON error.code 字段），不是继续扩子串表。上游将来改措辞时本分支会静默回落通用拒绝——届时按同一诊断流程（真打 API + 对照组）补关键词，不凭猜测扩表。

4. **文案自写，不透第三方原文。** 对外只给人话「这个模型不能用当前服务地址调用，请更换模型或调整服务地址。」，不带服务标签（该提示与具体服务无关，换聊天/语音服务都成立）；原始 message、帮助链接只进本机诊断，不出现在任何用户可见面。正式路径另给可区分错误码 `stt_model_interface_mismatch` / `tts_model_interface_mismatch` 供本机诊断。

5. **聊天侧错误面不变。** 新种类显式带 `ServiceErrorCategory.client` 公开类别（与通用兜底的 4xx→client 一致）：聊天 Provider 打到含 `url error` 的 4xx 时，错误对话框照旧弹「模型服务异常」并给前往设置入口；缺了这个类别，`_categorizeFallbackReason` 会落空，这条路径既无弹窗也无轻提示。降级归因保持通用 `FallbackReason.modelProvider`，不在行为契约新增条目。两个连带处随之钉住：正式语音路径的 client 前置分支用 `kind` 比较排除本种类，保住 `stt_model_interface_mismatch` / `tts_model_interface_mismatch` 可区分错误码；聊天页语音链路的 `categorizeVoiceApiError` 把这两个码映射到既有语音错误弹窗（与 `tts_client` 同一处理面），换码不换面。

## Consequences

- 同类失败（型号落在另一套 API 家族）在连接测试与正式转写/合成都给同一句可定位提示，用户知道该换模型还是该调服务地址；两种路径的错误码可区分，便于本机诊断。
- 分类表新增一条，既有 401/403、429、找不到模型、普通 400 的分类与文案逐字不变，由测试逐条锁定。
- 维护者若观察到新的「模型与接口不匹配」上游形态（换了措辞或换了厂商），集中修改点只有 `providerStatusFailure` 里的这一处关键词判定。
