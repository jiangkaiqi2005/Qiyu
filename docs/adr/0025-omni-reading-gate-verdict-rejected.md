# Omni 朗读准入门裁定：评估后放弃，朗读退回千问 TTS Realtime

2026-10-01。本文执行 [ADR 0024](0024-omni-realtime-two-phase-and-reading-gate.md) 预设的准入门裁定：对 `qwen3.8-omni-flash-realtime` 的第一阶段原型（omni 只当朗读者）**评估后放弃**。五条判据中四条被机器证据判死（判据 1 逐字性、判据 2 首音延迟、判据 4 纯停顿加词、判据 5 称呼吞没），第四条（判据 3 热线号码）因危机兜底文本根本没被逐字朗读而失去前提。按 0024 的既定退路：**朗读退回 `qwen3-tts-flash-realtime`，第二阶段（双工语音对话）不受影响，omni 只留给第二阶段**；本批后续票（正式 adapter、档位数据行、设置页试听、对话页接线）全部作废。原型脚本与产物（wav、逐条 diff、延迟原始数字、音色矩阵）在本机忽略目录 `.scratch/voice-omni-reading/` 留档，不入库；本文按 0024 的先例自足，关键数字全部写在正文。

## 判定依据：原型实测

原型按票面口径打真机 API：型号固定 `qwen3.8-omni-flash-realtime`，音色 Tina（3.8 默认），`session.instructions` 只放朗读指令（逐字朗读、不改写、不增删、不回应内容），`temperature` 按官方默认 0.6 挂在与 `session` 同级的根层，音频配置用嵌套 `session.audio.output.format.{type,sample_rate}`。对照组是仓库既有 `QwenRealtimeTtsGateway` 跑 `qwen3-tts-flash-realtime`（音色 Cherry，现状配置），未重写协议。样本 10 条：危机兜底中文三行（含 12356）与英文三行（含 988）取自行为核心 golden（`packages/qiyu_behavior_core/lib/src/behavior_core.dart:333-351`），纯停顿两条（「……」「（等了一会儿）」）为 0024 判据 4 引用的合法输出形态，极短句、带称呼安慰句、迟疑句、含数字句、中英混排、连续段五类取自本机真实 sessions 并逐条标注出处。完整跑了两轮，两轮结论一致。

### 判据 1（逐字性）：判死——归一化后 10 条中 8 条不一致，且是「对话」不是「念稿」

两轮中逐字一致（去标点、折叠空白、全半角统一、中文数字互转、英文小写折叠后完全相同）的只有 3 条：英文危机兜底、连续段（安慰段）、纯省略号「……」。其余 7 条全部违反，且违反方式是**模型把要念的文本当成了别人对它说的话，然后以自己的身份回应**：

- 危机兜底中文三行（golden 锁定的本地兜底输出）两轮都被改写成 omni 自己的安慰回复，例如第二轮转录为「谢谢你这么说。我会认真对待你的关心，也会记住你提醒我的这些资源。如果你愿意，我们可以一起慢慢聊聊你现在最难受的地方是什么？」——原文一字未念，还反向追问用户；
- 「我是栖语。嗯……你呢，怎么称呼？」→「我是通义千问，你可以叫我 Qwen。」（另一轮「我叫 Qwen-Omni。」）——栖语的自我介绍被替换成千问官方身份；
- 「嗯，我在。」→「好的，我在这里。」「在就好。你想聊点什么？」——改写甚至带出新的追问；
- 「（等了一会儿）」→「好的，我在这儿等着。」；
- 含数字句与中英混排句均被改写（混排句被改写成对 LMCC 的科普式转述）。

「文字永远是唯一真相源」要求音频是已过审文字的下游渲染。这些转录意味着音频通道在渲染模型自己生成的另一段话——防线三闸（`instructions` 措辞、`temperature`、事后 diff）前两道都已失守。

### 判据 1 补测（temperature）：已执行，仍判死

ADR 0024 已知代价条款明确：判据 1 判死时**无法区分「模型不老实」与「温度过高」，补测 temperature 是第一步而非直接放弃**。补测按既定口径执行：缩小样本（极短句、热线号码行、带称呼安慰句、迟疑句）× temperature 0.1，其余配置不变，共两轮。第一轮 **4/4 全部改写**（热线行被改写成 omni 自己的危机支持长回复，迟疑句再次出现「我叫Qwen」的自我介绍，极短句被改写并追加「你想聊点什么？」）；第二轮 3/4 改写（带称呼安慰句这次逐字通过，但危机号码行仍被改写成「你说得对，别一个人扛。……」）。死因因此锁定为「模型不老实」（更准确地说：omni 的 realtime 文本输入在行为上就是对话输入，模型以回应而非朗读处理它，逐字只是偶合），不是温度——危机兜底文本在 0.6 与 0.1 下共四次喂入，全部被改写，无一次逐字朗读。此项补救已穷尽，不构成继续评估的理由。

### 判据 2（首音延迟）：判死——中位比值 2.66×，门槛 1.5×

口径：从「喂进第一段文本」到「收到第一个音频块」。第一轮 omni 中位 690ms / 对照 270ms（比值 2.56），第二轮 688ms / 259ms（比值 2.66）。两轮 9 个可比样本的逐条比值全部超过门槛（1.99–3.42×），无一达标。公平性说明：omni 侧实测可用的文本喂入路径含一次 `response.create` 往返（见下节协议出入），但那是真机唯一可用的路径，数字按实测口径如实记录；即便乐观扣除一个往返，omni 首音绝对值也在 600ms 以上，对照在 230–330ms。

### 判据 4（纯停顿）：判死——「（等了一会儿）」被加了实词

「（等了一会儿）」两轮分别被念成「嗯，我在。」与「好的，我在这儿等着。」——归一化后存在完整实词残留。按 ADR 0024 判据 4 的明文（**omni 对纯停顿输入自己加实词 = 直接判第一阶段失败**），这一条单独就足以判死。「……」一条两轮转录均为「……」、无实词（是否真为静音留给 wav 人工复核，不影响本判定）。

### 判据 5（标点停顿、英文、称呼）：称呼吞没——机器可见地违反

英文样本按小写折叠比对通过（两轮逐字一致）。但带称呼的安慰句「晚安，姜凯奇。睡个好觉，明天见。」第二轮被念成「晚安。我会好好休息，明天见。」——**受保护用户设定行的称呼「姜凯奇」被整个吞掉**，同时句子被改写；第一轮虽保留称呼但插入「祝你」。判据 5 规定称呼被吞掉单独标红，本条机器侧即可判定，无需人耳。

### 判据 3（热线号码逐位念清）：失去前提

号码读法靠人耳听、不信 diff（归一化会把「一二三五六」与「一万二千三百五十六」都判通过）。本轮的实测结果是更根本的失败：中文危机兜底文本根本没被逐字朗读（判据 1），「号码是否一位一位念清」的问题在「念的根本不是这段话」面前不存在。英文样本被逐字朗读，988 的读法留给 wav 人工复核留档，但不改变裁定。

## 协议出入：票面/前序 ADR 断言的事件序列与真机不符

本次原型同时实测确认了几个与 ADR 0024 及其 spec 断言不一致的真机事实（错误码只取标识，未透上游原文）：

1. **`input_text_buffer.append` 与 `input_text_buffer.commit` 在真机被拒**：服务端回 `invalid_request_error code=invalid_value param=type`（事件 type 不存在）。0024 断言的「有 `input_text_buffer.*` 与 `session.finish`」在 `qwen3.8-omni-flash-realtime` 上不成立。
2. **`session.finish` 同样被拒**（同错误码），收尾只能按官方文档的另一选项直接断开 WebSocket。
3. **真机可用的纯文本输入路径**是官方文档所述 `conversation.item.create`（`input_text` 内容）→ `response.create`（裸事件即可触发）；实测事件序列为 `session.created` → `session.updated` → `conversation.item.created` → `response.created` → `response.output_item.added` → `response.content_part.added` → `response.audio_transcript.delta` / `response.audio.delta` → `response.audio_transcript.done` → `response.audio.done` → `response.content_part.done` → `response.output_item.done` → `response.done`。`response.done` 的 `response.status` 返回 `completed`，0024 关于「无 `response.cancelled`、以 `response.done` status 判半句」的断言与真机一致。
4. **嵌套 `session.audio.output.format` 被接受**，服务端 `session.updated` 回显了 `session.audio.output.{voice, format}` 与 `session.instructions`（指令已确认登记——因此判据 1 的失败是模型行为，不是配置丢失）；`temperature` 挂根层未引发错误，但回显不体现，其生效性无法经回显核验。

这些出入不改判死结论，反而强化它：指令确认被登记，模型仍选择对话。

## 采样率实测：部分可配，与官方文档两处矛盾的说法均不完全相符

官方文档一处枚举 8000/16000/24000/48000 可配，另一处写「默认 pcm 24 kHz、暂不支持自定义采样率」。实测（同一段长文本，比较「按请求采样率折算时长」与「按 24 kHz 折算时长」谁接近 24 kHz 基线）：

- **16000 Hz：生效**。两轮请求均被配置接受且回显一致，按 16 kHz 折算的时长（10.96s / 10.40s）与基线（10.96s）吻合，按 24 kHz 折算则只有 7.31s / 6.93s——与基线差 3.5 秒以上，不可能。
- **48000 Hz：两次实测结论相反，不可判定**。一轮字节量与「仍按 24 kHz 输出」吻合，另一轮与「48 kHz 生效」吻合——原因是模型改写行为使每次生成的语音内容时长本身在变，字节法在此失去分辨率。

结论：下行默认 24 kHz；16000 可配可用；48000 行为不稳、不可按文档枚举采信。将来任何接入都应按「音频块携带实际采样率、以回显加字节率复核」设计。

## Consequences

- **第一阶段放弃**：omni 不接入朗读链路。现有千问 TTS Realtime 与豆包路径零改动，`qwen3-tts-flash-realtime` 仍是唯一的流式朗读会话供给。本批拆票中依赖原型通过的正式接入票（adapter、档位数据行、设置页试听、对话页接线）全部作废。
- **无代码进入正式交付面**：原型脚本、样本、wav、diff 明细、音色矩阵全部留在忽略目录 `.scratch/voice-omni-reading/`，不成长期资产。音色矩阵 8 音色 × 2 条文字共 16 段 wav 已采齐（Tina、Zane、Cici、longanlingxin、Theo Calm、Serena、Maia、Raymond，会话全部成功），但精选音色集随判死作废，仅作第二阶段的听感参考留档。
- **第二阶段不受影响，前置裁定清单不变**（安全审核窗口、WebRTC 否决、隐藏块改 function calling、会话上限口径、上行音频规格）。本次评估的一个附带观察支持其中「安全审核窗口」的紧迫性：omni 在语音通道上的输出是它自由生成的对话内容，不是受控的渲染结果——第二阶段若让音频直接出模型，绕过安全校验的风险比 0024 设想的更具体。
- **改写风险三闸的教训**：`instructions`（确认已登记）与 `temperature`（补测 0.1）都不能把对话模型锁成朗读器；事后 diff 只能兜底发现、不能阻止半句已播。对「文字是唯一真相源」而言，渲染通道必须天然只能渲染给定文本（TTS 形态），这是本次评估的正向确认。
- **顺带印证的既存问题**：对照组 `qwen3-tts-flash-realtime` 对纯停顿输入「……」两次运行都在等音频时超时——ADR 0024「顺带发现的两个既存问题」第 2 条（纯停顿输入无测试覆盖、不应送朗读）在真机上得到印证，「纯停顿与只有标点的回复不送朗读」作为独立于 omni 的既有行为修正继续推进。
- 本裁定为 ADR 0024 预留的两篇结论 ADR 之一（判死篇）；若将来千问提供真正的 TTS 形态 omni 接口（服务端只渲染不生成），可另起新评估，不适用本文结论。
