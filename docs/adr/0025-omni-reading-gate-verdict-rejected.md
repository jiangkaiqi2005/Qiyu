# Omni 朗读准入门裁定：评估后放弃，朗读退回千问 TTS Realtime

2026-10-01。本文执行 [ADR 0024](0024-omni-realtime-two-phase-and-reading-gate.md) 预设的准入门裁定：对 `qwen3.8-omni-flash-realtime` 的第一阶段原型（omni 只当朗读者）**评估后放弃**。五条判据中四条被机器证据判死（判据 1 逐字性、判据 2 首音延迟、判据 4 纯停顿加词、判据 5 称呼吞没），第四条（判据 3 热线号码）因危机兜底文本根本没被逐字朗读而失去前提。按 0024 的既定退路：**朗读退回 `qwen3-tts-flash-realtime`，第二阶段（双工语音对话）不受影响，omni 只留给第二阶段**；本批后续票（正式 adapter、档位数据行、设置页试听、对话页接线）全部作废。原型脚本与产物（wav、逐条 diff、延迟原始数字、音色矩阵）在本机忽略目录 `.scratch/voice-omni-reading/` 留档，不入库；本文按 0024 的先例自足，关键数字全部写在正文。

## 判定依据：原型实测

原型按票面口径打真机 API：型号固定 `qwen3.8-omni-flash-realtime`，音色 Tina（3.8 默认），`session.instructions` 只放朗读指令（逐字朗读、不改写、不增删、不回应内容），`temperature` 按官方默认 0.6 挂在与 `session` 同级的根层，音频配置用嵌套 `session.audio.output.format.{type,sample_rate}`。对照组是仓库既有 `QwenRealtimeTtsGateway` 跑 `qwen3-tts-flash-realtime`（音色 Cherry，现状配置），未重写协议。危机兜底中文三行（含 12356）与英文三行（含 988）取自行为核心 golden（`packages/qiyu_behavior_core/lib/src/behavior_core.dart:349-351` 与 `:331-333`），纯停顿两条（「……」「（等了一会儿）」）为 0024 判据 4 引用的合法输出形态，其余取自本机真实 sessions 并逐条标注出处：极短句、带称呼安慰句、迟疑句、含数量数字句、含钟点时刻句、中英混排、连续段——除 0024 所述五类外，含数量数字句与含钟点时刻句为本票为覆盖归一化「中文数字与阿拉伯数字互转」「23:40↔二十三点四十」分支扩入；钟点时刻样本在评审后补入第二轮（第一轮为 10 条、无钟点样本），「23:40」式时间互转分支由此在真机端到端覆盖。

**证据留档口径**：主对照共三轮、温度补测共三轮。先行主对照一轮与先行温度补测一轮因一次性清理失误未留档，其数字（主对照：中位 690/270ms、比值 2.56×、逐条 1.71–3.42×、7/10 逐字不一致；补测：4/4 改写）与留档轮结论一致，但无法事后复核，**本文判定依据全部取自两轮完整留档**：`proto/out-round-1/` 与 `proto/out/`（各含 report.md、samples.jsonl、全部 wav 与 temperature-supplement.md）。`out-round-1/` 的 samples.jsonl 中 crisis-en 出处字段仍是订正前的 `:333-335`，以本文行号为准。

### 判据 1（逐字性）：判死——留档两轮的 10 条共同样本各 7 条归一化后不一致，且是「对话」不是「念稿」

两轮留档主对照中，逐字一致（去标点、折叠空白、全半角统一、中文数字互转、英文小写折叠后完全相同）的都只有 3 条，但组成有波动：第一轮 PASS 为英文危机兜底、连续段、纯省略号「……」；第二轮 PASS 为英文危机兜底、连续段、危机兜底中文三行——**危机中文行第一轮被改写、第二轮逐字通过，而「……」第一轮通过、第二轮被加词**（逐样本判定不稳定，门级结论两轮一致）。10 条共同样本中 8 条在至少一轮被改写，逐字稳定通过的只有英文危机兜底与连续段；第二轮新增的钟点样本亦被改写。违反方式是**模型把要念的文本当成了别人对它说的话，然后以自己的身份回应**：

- 危机兜底中文三行（golden 锁定的本地兜底输出）第一轮被改写成 omni 自己的安慰回复：「谢谢你这么说。我会认真对待你的关心，也会记住你提醒我的这些资源。如果你愿意，我们可以一起慢慢聊聊你现在最难受的地方是什么？」——原文一字未念，还反向追问用户；
- 「我是栖语。嗯……你呢，怎么称呼？」两轮分别被念成「我是通义千问，你可以叫我 Qwen。」与「我叫 Qwen-Omni，你可以叫我小奥。」——栖语的自我介绍被替换成千问官方身份；
- 「嗯，我在。」两轮分别被念成「好的，我在这里。」与「好，我在听。你想聊点什么？」——改写甚至带出新的追问；
- 含数量数字句两轮均被改写（第二轮还自行追加换算「算下来一小时1.25元」）；含钟点时刻句「9:30-11:30」被改写成叙述句「时间是从9点30分到11点30分」并增词；中英混排句被改写成对 LMCC 的科普式转述。

「文字永远是唯一真相源」要求音频是已过审文字的下游渲染。这些转录意味着音频通道在渲染模型自己生成的另一段话——防线三闸（`instructions` 措辞、`temperature`、事后 diff）前两道都已失守。

### 判据 1 补测（temperature）：已执行，仍判死

ADR 0024 已知代价条款明确：判据 1 判死时**无法区分「模型不老实」与「温度过高」，补测 temperature 是第一步而非直接放弃**。补测按既定口径执行：缩小样本（极短句、热线号码行、带称呼安慰句、迟疑句）× temperature 0.1，其余配置不变，共三轮——先行轮 4/4 改写（未留档），留档两轮分别 3/4 与 4/4 改写。热线号码行**三轮全部被改写**（留档两轮分别为「你说得对，别一个人扛。全国 24 小时心理援助热线是 12356……」与「好，我不一个人扛。」）；迟疑句两轮留档均出现千问自我介绍（「我叫Qwen，你可以这么叫我」/「我叫Qwen-Omni，你可以叫我小O」）；带称呼安慰句一轮被念成孤零零的「晚安。」。死因因此锁定为「模型不老实」（更准确地说：omni 的 realtime 文本输入在行为上就是对话输入，模型以回应而非朗读处理它，逐字只是偶合），不是温度——危机兜底中文文本在 0.6 与 0.1 下共五次喂入（主对照两轮、补测三轮），四次被改写、仅一次逐字朗读。此项补救已穷尽，不构成继续评估的理由。

### 判据 2（首音延迟）：判死——留档两轮中位比值 2.66× / 2.78×，门槛 1.5×

口径：从「喂进第一段文本」到「收到第一个音频块」。留档第一轮 omni 中位 688ms / 对照 259ms（比值 2.66×），9 个可比样本逐条 1.99–3.42×；留档第二轮 omni 中位 729ms / 对照 262ms（比值 2.78×），10 个可比样本逐条 2.15–3.15×。两轮共 19 个可比比值全部超过门槛，无一达标。公平性说明：omni 侧实测可用的文本喂入路径含一次 `response.create` 往返（见下节协议出入），但那是真机唯一可用的路径，数字按实测口径如实记录；且 omni 的最低首音（587ms）仍高于对照的最高首音（355ms）——逐对全慢的结论不依赖往返成本如何分摊。

### 判据 4（纯停顿）：判死——两条纯停顿样本跨轮都被加了实词

「（等了一会儿）」两轮留档分别被念成「好的，我在这儿等着。」与「嗯，我在。」——归一化后均有完整实词残留；「……」第一轮通过（转录仍为「……」），第二轮被念成「嗯，我在听。」。两条纯停顿样本在两轮中都至少一次被加了实词，直接判死条件在两轮中分别命中。按 ADR 0024 判据 4 的明文（**omni 对纯停顿输入自己加实词 = 直接判第一阶段失败**），这一条单独就足以判死。

### 判据 5（标点停顿、英文、称呼）：称呼吞没——机器可见地违反

英文样本按小写折叠比对通过（两轮逐字一致）。但带称呼的安慰句「晚安，姜凯奇。睡个好觉，明天见。」第一轮被念成「晚安。我会好好休息，明天见。」——**受保护用户设定行的称呼「姜凯奇」被整个吞掉**，同时句子被改写；第二轮保留称呼但插入「祝你」并改句尾（「祝你睡个好觉，明天见！」）；补测第二轮更被念成只剩「晚安。」。判据 5 规定称呼被吞掉单独标红，本条机器侧即可判定，无需人耳。

### 判据 3（热线号码逐位念清）：失去前提

号码读法靠人耳听、不信 diff（归一化会把「一二三五六」与「一万二千三百五十六」都判通过）。本轮的实测结果是更根本的失败：危机兜底中文文本五次喂入中四次被改写成 omni 自己的回复、仅一次逐字朗读（主对照第二轮），「号码是否一位一位念清」的问题在「念的根本不是这段话」面前大概率不存在。英文样本两轮均被逐字朗读，988 的读法留给 wav 人工复核留档，但不改变裁定。

## 协议出入：票面/前序 ADR 断言的事件序列与真机不符

本次原型同时实测确认了几个与 ADR 0024 及其 spec 断言不一致的真机事实（错误码只取标识，未透上游原文）：

1. **`input_text_buffer.append` 与 `input_text_buffer.commit` 在真机被拒**：服务端回 `invalid_request_error code=invalid_value param=type`（事件 type 不存在）。0024 断言的「有 `input_text_buffer.*` 与 `session.finish`」在 `qwen3.8-omni-flash-realtime` 上不成立。
2. **`session.finish` 同样被拒**（同错误码），收尾只能按官方文档的另一选项直接断开 WebSocket。
3. **真机可用的纯文本输入路径**是官方文档所述 `conversation.item.create`（`input_text` 内容）→ `response.create`（裸事件即可触发）；实测事件序列为 `session.created` → `session.updated` → `conversation.item.created` → `response.created` → `response.output_item.added` → `response.content_part.added` → `response.audio_transcript.delta` / `response.audio.delta` → `response.audio_transcript.done` → `response.audio.done` → `response.content_part.done` → `response.output_item.done` → `response.done`。`response.done` 的 `response.status` 返回 `completed`，0024 关于「无 `response.cancelled`、以 `response.done` status 判半句」的断言与真机一致。
4. **嵌套 `session.audio.output.format` 被接受**，服务端 `session.updated` 回显了 `session.audio.output.{voice, format}` 与 `session.instructions`（指令已确认登记——因此判据 1 的失败是模型行为，不是配置丢失）；`temperature` 挂根层未引发错误，但回显不体现，其生效性无法经回显核验。

这些出入不改判死结论，反而强化它：指令确认被登记，模型仍选择对话。

## 采样率实测：两档留档探针均生效，与官方文档「暂不支持自定义」的说法不符

官方文档一处枚举 8000/16000/24000/48000 可配，另一处写「默认 pcm 24 kHz、暂不支持自定义采样率」。实测（同一段长文本，比较「按请求采样率折算时长」与「按 24 kHz 折算时长」谁接近 24 kHz 基线）：

- **16000 Hz：生效**。两轮留档探针按 16 kHz 折算的时长分别为 10.40s / 11.12s，与各自 24 kHz 基线（10.96s / 11.04s）吻合；按 24 kHz 折算则只有 6.93s / 7.41s——与基线差 3.5 秒以上，不可能。先行未留档一轮同样判生效（10.96s 与基线完全吻合）。
- **48000 Hz：两轮留档探针均判生效**（按 48 kHz 折算 8.96s / 11.76s，接近各自基线 10.96s / 11.04s；按 24 kHz 折算 17.92s / 23.52s，明显偏离），先行未留档一轮曾判未生效（该轮字节量与 24 kHz 折算吻合）——模型改写行为使每次生成的内容时长在变，字节法分辨率有限，一次相反观测无法排除。

结论：下行默认 24 kHz；16000 生效（三轮一致）；48000 留档两轮生效、另有一次相反观测。将来任何接入都应按「音频块携带实际采样率、以回显加字节率复核」设计，不按文档枚举盲信。

## Consequences

- **第一阶段放弃**：omni 不接入朗读链路。现有千问 TTS Realtime 与豆包路径零改动，`qwen3-tts-flash-realtime` 仍是唯一的流式朗读会话供给。本批拆票中依赖原型通过的正式接入票（adapter、档位数据行、设置页试听、对话页接线）全部作废。
- **无代码进入正式交付面**：原型脚本、样本、wav、diff 明细、音色矩阵全部留在忽略目录 `.scratch/voice-omni-reading/`，不成长期资产。音色矩阵 8 音色 × 2 条文字在两轮留档中共 32 段 wav（Tina、Zane、Cici、longanlingxin、Theo Calm、Serena、Maia、Raymond，16 个会话 × 2 轮全部成功），但精选音色集随判死作废，仅作第二阶段的听感参考留档。
- **第二阶段不受影响，前置裁定清单不变**（安全审核窗口、WebRTC 否决、隐藏块改 function calling、会话上限口径、上行音频规格）。本次评估的一个附带观察支持其中「安全审核窗口」的紧迫性：omni 在语音通道上的输出是它自由生成的对话内容，不是受控的渲染结果——第二阶段若让音频直接出模型，绕过安全校验的风险比 0024 设想的更具体。
- **改写风险三闸的教训**：`instructions`（确认已登记）与 `temperature`（补测 0.1）都不能把对话模型锁成朗读器；事后 diff 只能兜底发现、不能阻止半句已播。对「文字是唯一真相源」而言，渲染通道必须天然只能渲染给定文本（TTS 形态），这是本次评估的正向确认。
- **顺带印证的既存问题**：对照组 `qwen3-tts-flash-realtime` 对纯停顿输入「……」三轮运行都在等音频时超时——ADR 0024「顺带发现的两个既存问题」第 2 条（纯停顿输入无测试覆盖、不应送朗读）在真机上得到印证，「纯停顿与只有标点的回复不送朗读」作为独立于 omni 的既有行为修正继续推进。
- 本裁定为 ADR 0024 预留的两篇结论 ADR 之一（判死篇）；若将来千问提供真正的 TTS 形态 omni 接口（服务端只渲染不生成），可另起新评估，不适用本文结论。
