# 窄屏字阶独立成档、按上下文取档，而非全局缩放或桌面档通用

手机 Edge 实测反馈字号太大（2026-09-04 定稿，grill-with-docs 拷问六题）。决定：窗口宽 < 760px（与壳层抽屉同一道缝、同一个「窄屏」概念）时五档字阶走移动档 20/16/14/12/11，桌面档 22/18/15/13/12 原值不动；只动字号，行高 1.9、字重、字距、间距几何全部不变。实现取「数值双档 + 样式形状单份工厂 + 消费方按上下文取档」，主题函数加窄屏参数由 app builder 传入（与 reduce-motion 同模式）。理由：字阶是逐档定夺的设计事实，等比缩放会出非整数并毁掉极小档可读性；与 760 同缝保证不会出现「抽屉出来了、字还是桌面档」的半窄状态；形状单份保证改字重字距不会漏改另一档。代价是消费方从直读 const 样式改为按上下文取档，约 8 处调用点机械替换。

## Considered Options

- 全局 `TextScaler` 等比缩放（约十几行的探针方案）：改动最小、立即可试，被否——极小档 12 缩到约 10 手机上难读，输入框占位字行盒按「按钮高度 ÷ 字号」比值计算会漂移，且字号不可控、无法逐档定夺。
- 页面全面改走 `Theme.of(context).textTheme` 语义槽位：理论上最正统（主题层已有「不许绕过 Theme 取色」纪律），被否——把存量重构混进新功能交付，违反外科手术纪律；留作以后的独立清理。
- 维持桌面档通用（现状）：被否——手机端主诉未解，且违背 §3「精美优先，宁小勿大」在窄屏上的精神。

## Consequences

- design-system §3 新增窄屏字表，与桌面表并列；「精美优先，宁小勿大」原则对两档同样生效。
- 样式形状今后只许在单份工厂里改；直读 const 字号样式成为反模式，新增样式必须走按上下文取档入口。
- 桌面窄窗口（< 760）与手机同待遇：字阶随抽屉一起切窄屏形态——有意接受，与壳层既有行为一致。
- 宽度判据继续收敛于同一 token 常量；引入触屏检测当第二判据被词汇表「窄屏」条目明确禁止。
- 窄屏数值集是单点可调的真机手感旋钮：迭代手感只改这一处数值，不触结构。
