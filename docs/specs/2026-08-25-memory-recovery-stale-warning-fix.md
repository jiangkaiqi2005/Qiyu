# 修正未归档日期触发的记忆损坏误报 Spec

## Problem Statement

用户打开记忆中心时看到红色提示“部分记忆文件出现过损坏”，但本机记忆正文实际上可以正常读取，最近发生、长期印象、关于你和关系内容也仍然存在。这个提示会让用户合理地怀疑原始聊天或长期记忆已经丢失。

现场诊断确认，本次没有发生 Markdown 语法损坏、编码损坏、内容截断或证据丢失。恢复报告只有一项 `stale + full`：2026 年 8 月的每日索引曾落后于现存 episode，系统已经从有效每日记录完整重建；隔离文件为 0，无法恢复内容为 0。当前全部 Markdown 均可按严格 UTF-8 读取，episode 日期与每日索引完全一致。

误报由两层语义不一致共同造成：

1. 正常索引只纳入已完成日终归档的 episode；当天或待补扫日期即使已有有效条目，只要 `finalized` 仍为 false，就应暂时不进入索引。
2. 启动恢复扫描却把所有“可读且有有效条目”的 episode 都视为索引必须成员，没有排除尚未归档的日期。恢复扫描又先于启动补归档运行，因此一个正常的待归档日期会稳定制造“索引 stale”。

本次现场中，恢复扫描于 2026-08-25 11:44:36 完成；`2026-08-24` 随后才在 11:50:59 完成启动补归档。这与“恢复先把待归档日期误判为索引落后，随后补归档正常完成”的时序一致。

界面又放大了误解：恢复报告只要包含任意 finding 就被视为不健康，记忆中心也只要看到任意 finding 就显示损坏横幅，不区分“仍待恢复”“部分恢复”和“已经完整恢复”。报告作为最近一次扫描历史会持续存在，所以即使当前索引已经健康，红色损坏提示仍不会消失。

## Solution

统一正常索引、恢复校验和恢复重建对“哪些日期应该进入持久索引”的定义：只有可读、含有效条目且已完成日终归档的 episode 才是稳定索引成员；正在执行日终归档的日期仍通过既有事务内例外参与本次索引写入。普通未归档日期缺席索引是健康状态，不能产生 `stale`、恢复日志或用户告警。

同时把“扫描发现过问题”和“当前仍不健康”拆开表达：

- 没有 finding、没有隔离原件时是健康状态，不显示恢复提示。
- finding 全部为完整恢复且没有隔离原件时是已恢复状态，不显示红色损坏警告；如保留设计要求的简短结果，只能使用中性“已完成记忆整理/恢复”语义。
- 存在待恢复、部分恢复或仍保留的隔离原件时才是需要用户关注的状态，显示受影响层、恢复结果和仍无法恢复的内容。

既有 `stale + full + quarantinedFiles: 0` 报告必须按已恢复状态解释，使升级后的应用即使先读到旧报告，也不会继续显示当前损坏。真正的索引语法损坏、已归档日期缺失、孤儿引用、内容截断和部分恢复仍按原有 T26 规则检测、隔离、重建和提示，不能通过简单隐藏所有 `stale` 或所有 finding 来规避问题。

## User Stories

1. 作为使用记忆中心的用户，我希望只有当前确有未恢复损坏时才看到红色警告，从而不会误以为聊天或长期记忆已经丢失。
2. 作为当天仍在聊天的用户，我希望尚未日终归档的 episode 不会被恢复扫描当作索引损坏，从而正常使用不会制造故障提示。
3. 作为应用重启后的用户，我希望启动补扫前存在的待归档日期被视为正常中间状态，从而不会每次启动都触发同类误报。
4. 作为已成功完成自动恢复的用户，我希望界面明确区分“已经恢复”和“仍然损坏”，从而能正确判断是否需要处理。
5. 作为已有 `stale + full` 历史报告的用户，我希望升级后无需删除记忆或手工编辑报告就能消除错误的损坏警告。
6. 作为遭遇真实 Markdown 损坏的用户，我希望语法错误、截断或引用失效仍能被检测并按证据恢复，从而本次修正不会削弱数据保护。
7. 作为存在部分恢复结果的用户，我希望隔离原件继续保留，界面继续说明未恢复损失，从而不会用“已修复”掩盖真实风险。
8. 作为只发生派生索引落后的用户，我希望系统能够安全重建索引但不把派生层整理描述成原始记忆损坏。
9. 作为查看恢复详情的用户，我希望看到的状态反映当前可用性，而恢复历史仍可由本机日志保留，从而历史记录与当前健康状态不会混为一谈。
10. 作为依赖旧版本报告文件的用户，我希望报告格式继续向后兼容，从而升级不需要迁移或清空本地记忆目录。
11. 作为无 Provider 配置的用户，我希望这项结构恢复与状态判断完全在本机完成，从而不会因为修复误报而新增模型或网络依赖。
12. 作为维护者，我希望待归档 episode、真实 stale 索引和部分恢复各有自动回归测试，从而以后调整启动顺序或日终流程时不会再次混淆。

## Implementation Decisions

- 持久化两级索引的规范成员必须与日终归档契约一致：episode 可读、含至少一条有效条目且已 `finalized`。正在提交的当天只能通过现有的事务内“正在归档日期”例外进入索引。
- 恢复扫描判断索引缺失行、孤儿行和 stale 时必须复用上述规范成员口径，不得自行把所有未归档 episode 纳入期望集合。
- 索引恢复后的重建结果必须符合相同的稳定成员口径。召回流程为临时自修复而包含未归档日期的特殊能力属于独立场景，不得反向改变启动健康检查的定义。
- 保留恢复先于启动补归档的总体顺序，避免尚未完成底层损坏处理就让日终流程读取受损文件；本次修正应优先消除两套成员规则不一致，而不是仅交换异步任务顺序。
- 恢复报告必须区分历史 findings 与当前需关注状态。当前健康不能继续简单等价于 `findings.isEmpty`。
- “需关注”至少包含待恢复、部分恢复或隔离区仍保留原件；全部 finding 均为完整恢复且隔离区为空时，当前运行状态应视为可用。
- 记忆中心的红色损坏横幅只表达当前需关注状态。完整恢复结果若继续展示，必须使用中性文案和非错误视觉，不得使用“部分记忆文件出现过损坏”暗示当前仍损坏。
- 旧版持久化报告不要求迁移。读取端应能从已有 outcome、quarantined 和隔离文件计数推导正确状态，尤其正确处理 `full + 0 隔离`。
- 恢复日志继续记录时间、记忆类型、结果和损失，不记录正文；本次不删除或重写用户已有恢复历史。
- 不改变 sessions、episodes、热层、PersonaTree、long-memory 的恢复证据优先级，不放宽冻结、禁提、删除墓碑与敏感信息过滤。
- 不通过删除报告、清空记忆目录、忽略全部 stale finding 或关闭启动恢复来消除提示。

## Testing Decisions

- 主测试 seam 使用现有 Windows Host 记忆恢复服务，在隔离的临时记忆目录验证恢复报告、索引文件、隔离计数和恢复日志。测试外部可观察结果，不断言私有辅助函数或具体循环次数。
- 核心回归场景：存在一个可读、含有效条目但尚未 finalized 的日期；现有索引正确地不含该日期。运行恢复扫描后报告不得产生索引 stale/missing finding，不得重写健康索引，不得写损坏日志，也不得创建隔离原件。
- 真实 stale 场景：一个已 finalized 且含有效条目的日期缺席索引。恢复扫描必须检测并完整重建；重建后的索引包含该日期，结果为完整恢复且无数据损失。
- 真实损坏场景：索引文件无法解析时仍从有效 finalized episodes 重建，继续遵守隔离和完整恢复后清理原件的既有规则。
- 部分恢复与待恢复场景继续验证隔离原件保留、损失说明存在、当前状态需要关注，防止本次状态拆分隐藏真实故障。
- 第二个 seam 使用现有 Flutter 记忆中心 widget 测试：健康报告不显示提示；旧版 `stale + full + 0 隔离` 报告不显示红色损坏横幅；部分恢复、待恢复或隔离原件仍显示警告与详情。
- 如果产品保留完整恢复的中性提示，widget 测试必须断言其文案不含“损坏”或其他当前故障语义，并使用非错误视觉层级。
- 增加启动顺序集成覆盖：恢复扫描面对未归档旧日后，启动补归档仍能正常完成，最终索引只包含契约允许的日期且不会留下错误健康状态。
- 保留现有健康记忆库、缺失索引、孤儿索引、损坏索引和恢复报告解析测试；专项测试通过后运行 Windows Host 与 Flutter 的 analyze/test，最后运行完整 Release 1 门禁。
- 所有测试使用临时目录与合成摘要，不读取或复制用户真实 sessions、Provider 配置、API Key 或记忆正文。

## Out of Scope

- 修改日终归档、checkpoint、Dream、月压缩、PersonaTree 或长期记忆的业务内容。
- 改变正常聊天中 episode 何时产生、何时 finalized，或让对话中实时维护持久索引。
- 重新设计召回模型、索引关键词、检索路径或跨月查找策略。
- 删除、迁移或清空用户现有恢复日志、报告、sessions 或 episodes。
- 将恢复状态上传到远程服务，或新增 Provider/LLM 调用。
- 为所有恢复历史建设独立历史页面、通知中心或用户确认流程。
- 修复与本误报无关的记忆摘要质量、关系阶段判断或可见卡片文案。

## Further Notes

- 本 Spec 修正的是“健康状态与历史恢复事件混淆”，不是取消 T26 损坏恢复。
- `stale` 本身仍是有意义的派生层诊断：已归档证据缺席索引时应触发重建；只有未归档日期按设计缺席索引时不应被标记。
- 设计笔记明确：对话中不更新 index，日终归档成功后才更新 index 并将日期标为 finalized；因此恢复扫描必须尊重同一生命周期。
- 设计笔记也明确：完整恢复后删除隔离原件，部分恢复保留原件并提示用户。界面可以保留完整恢复的简短结果，但不能把它渲染为仍在发生的损坏。
- 本次现场数据只用于定位根因，不得写入测试 fixture、提交、PR 或日志；回归测试使用脱敏合成数据。
