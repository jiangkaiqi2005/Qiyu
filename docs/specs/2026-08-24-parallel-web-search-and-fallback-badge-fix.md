# 修复并行联网搜索降级与本地回复标识误导 Spec

## Problem Statement

用户已经正确配置火山方舟 Agent Plan、`deepseek-v4-flash` 与 API Key。模型连接测试成功，普通消息也能得到模型回复，但请求联网搜索后，栖语会突然退回只说“嗯？”的本地规则回复。之后的追问也可能继续降级。关闭并重新启动 Windows Host 后，这种现象看起来更明显，容易让用户误以为 API Key、配置持久化或 EXE 启动流程失效。

现场诊断已经排除这些方向：重启前后 Provider 配置内容完全一致；重启后的 Host 能读取已保存的 Key；模型连接测试成功；服务地址可直连；运行中的 EXE 包含当前联网搜索实现。两次真实聊天降级均被开发者诊断记录为 `incompatible_model_response`。

根因是 Anthropic-compatible 工具流的并行调用没有被正确建模。火山方舟的 `deepseek-v4-flash` 会在同一次回复里生成两个 `web_search` `tool_use` block。当前解析器只保留一组工具 ID、名称和参数缓冲区：后一个工具会覆盖前一个工具的标识，而两个工具的 `input_json_delta` 会被追加到同一字符串。随后运行时把两个相邻 JSON 对象当作一个对象解析，触发格式异常，并将本来有效的模型响应归类为 `incompatible_model_response`，最终按安全降级策略交付本地规则回复。

另有一个独立的界面问题放大了误解：聊天页顶部“本地规则回复”不是根据最近一次已完成的栖语回复判断，而是扫描当前会话中是否曾经出现过任意本地回复。只要历史中有过一次降级，即使之后模型已经正常回复，该标识仍会一直存在。

## Solution

让 Windows Host 正确处理一次 Anthropic-compatible 响应中的多个 `tool_use` block：每个工具调用拥有独立的 ID、名称和参数增量缓冲区，不能互相覆盖或拼接。对于当前已经注册的 `web_search` 工具，运行时应为模型返回的每个有效调用执行搜索，并在后续模型请求中按原工具 ID 返回一一对应的 `tool_result`。现有超时、取消、脱敏、安全校验和本地降级边界继续生效。

同时将聊天页顶部标识改为表达最近一次已完成的栖语回复来源。最近一次回复来自本地规则时显示“本地规则回复”；后续模型回复成功后立即隐藏；刷新或 Host 重启后根据恢复出的最后一条栖语消息得到相同结果。

修复后，用户使用支持并行工具调用的 Anthropic-compatible 模型搜索当前信息时，不会因为响应中包含多个合法 `web_search` 而降级。用户仍能在真正发生本地降级时看到明确标识，但不会被更早的历史降级持续误导。

## User Stories

1. 作为已经配置模型的用户，我希望联网搜索支持模型一次提出多个查询，从而不会因为模型的合法工具行为突然收到“嗯？”。
2. 作为火山方舟 Agent Plan 用户，我希望连接测试成功后，实际聊天也能兼容该模型返回的 Anthropic SSE 工具事件。
3. 作为请求当前新闻的用户，我希望栖语能完成搜索并给出经过安全校验的自然回复，而不是静默退回本地规则。
4. 作为在搜索失败后继续追问的用户，我希望前一轮未完成的搜索上下文不会让后续普通对话持续降级。
5. 作为用户，我希望每个模型工具调用都得到与原 `tool_use_id` 对应的结果，从而保持 Provider 协议完整。
6. 作为用户，我希望多个搜索中的单个搜索失败时仍遵守现有错误处理边界，从而不会泄露第三方错误、Key 或本机信息。
7. 作为用户，我希望停止生成时能够取消尚未完成的并行搜索和后续模型请求，从而不会在后台继续无意义工作。
8. 作为用户，我希望顶部“本地规则回复”只描述最近一次栖语回复，从而能正确判断当前是否仍在降级。
9. 作为已经恢复正常模型回复的用户，我希望旧的本地回复不会让顶部标识永久残留。
10. 作为刷新页面或重启 Host 的用户，我希望回复来源标识与重启前一致，从而不会因恢复逻辑产生新的误导。
11. 作为未配置 Provider 的用户，我希望本地规则回复与其标识继续正常工作，从而不破坏无模型时的完整可用性。
12. 作为维护者，我希望并行工具事件拥有自动回归测试，从而以后更换或增加 Anthropic-compatible 模型时不会重复出现同类降级。

## Implementation Decisions

- Anthropic SSE 解析结果必须能够表达同一模型 turn 中的多个内容块和多个工具调用，不再使用单例工具 ID、名称和参数缓冲区代表整轮响应。
- 工具参数增量按内容块索引或工具调用 ID 独立累计；`thinking`、可见文本和其他非工具内容不得混入工具参数。
- 每个完成的 `tool_use` 必须独立校验名称与输入 schema。未知工具继续失败关闭，不能被当作 `web_search` 执行。
- 当前只执行已注册的 `web_search`。一次响应中的多个合法搜索都应保留各自的工具 ID，并生成一一对应的 `tool_result`；不得把多个查询拼成一个 JSON，也不得把结果错配给其他 ID。
- 多搜索继续复用现有请求超时、取消信号、敏感查询清洗和第三方错误脱敏。具体采用串行还是有界并行可由实现者结合现有抽象决定，但取消必须覆盖全部未完成工作。
- 第二轮模型请求必须遵守 Anthropic Messages 工具协议：保留第一轮 assistant 的全部工具调用，并提供与之对应的全部结果。不得只回传最后一个调用。
- Provider 返回真正不兼容的事件、无效 JSON、未知工具或缺失终止标记时，继续使用现有失败分类和本地降级，不放宽安全完成条件。
- 不通过关闭联网搜索、改模型、重存 Key或绕过完整候选校验来规避问题。
- 聊天页的回复来源标识改为由最近一条已完成的栖语消息决定，而不是由会话中任意历史消息决定。
- 流式发送期间保持上一次已完成回复的标识；新回复完成并提交后再更新，避免等待态和半句候选改变状态。
- 会话恢复沿用已持久化的消息来源信息。若恢复数据没有可靠来源，不应凭文本内容猜测。
- 不改变 Provider 配置格式、API Key 存储、聊天事件协议字段、行为核心的本地规则内容或人格边界。

## Testing Decisions

- 好测试验证公开事件、搜索调用、Provider 请求体、最终回复来源和可见标识，不断言私有字段名或内部循环次数。
- 主测试 seam 使用现有联网搜索模型网关测试：构造一轮包含 `thinking`、可见文本、两个不同索引的 `web_search`、分段 `input_json_delta`、`tool_use` 停止原因和原生 `message_stop` 的 Anthropic SSE。
- 主回归测试必须证明两个工具参数分别组成合法 JSON、两次搜索都收到正确查询、第二轮模型请求包含两个原始 `tool_use` 和两个匹配的 `tool_result`，最终交付模型回复而不是 `incompatible_model_response`。
- 增加取消覆盖：多个搜索中任一阶段收到停止信号后，所有未完成搜索与第二轮 Provider 请求都结束，不提交半句模型回复。
- 保留单工具、无工具、未知工具、参数格式错误、搜索失败、第二轮重复工具调用、提前 EOF 和 Provider 原生错误测试，防止并行支持放宽原有失败边界。
- 第二个 seam 使用现有 Flutter 聊天页 widget 测试：历史包含本地回复但最后一条为模型回复时不显示标识；最后一条为本地回复时显示；随后成功模型回复后隐藏；刷新恢复结果一致。
- Host 专项测试通过后运行 Windows Host analyze/test 与 Flutter analyze/test，最后运行完整 Release 1 门禁，包含 Web 构建、Windows bundle、preflight 和 launch smoke。
- 测试只使用 fake HTTP、fake 搜索客户端和合成 SSE，不读取用户真实 `provider.json`、API Key、sessions 或记忆目录。

## Out of Scope

- 更换火山方舟模型、修改用户套餐或重新配置 API Key。
- 禁用 AnySearch 或移除联网搜索能力。
- 引入通用 Agent 工具框架、任意第三方工具或递归工具循环。
- 重新设计联网搜索产品交互、展示搜索进度或向用户暴露工具调用日志。
- 修改栖语人格、system prompt、记忆机制、关系阶段或本地规则话术。
- 修改开发者诊断的存储方式或新增原始 Provider 响应日志。
- 将“本地规则回复”改成实时 Provider 健康指示器；它只表达最近一次已完成回复的来源。
- 处理与本问题无关的 STT、TTS、Dream 或日终整理行为。

## Further Notes

- 现场连接测试成功，证明 API Key、模型名称、基础 Anthropic SSE 和完整候选校验可用；失败只发生在聊天启用联网搜索工具的路径。
- 最小真实 Provider 请求返回 HTTP 200，并连续产生两个 `web_search` `tool_use` block；三轮最小上下文“搜索请求 → 本地短回复 → 用户追问”同样稳定产生两个工具调用。这是本 Spec 的已验证根因，不是推测。
- 当前测试明确覆盖“一次工具调用、一次搜索”，但没有覆盖同一模型 turn 中的多个工具调用。这一缺口应由本次回归测试关闭。
- 不得把真实 API Key、Provider 原始正文、用户聊天正文或开发者诊断快照提交进 fixture、日志、Spec、commit 或 PR。
- 顶部标识问题与并行工具解析问题相互独立：前者造成状态误导，后者造成真实降级。实现和测试可以分开完成，但交付时应一起验证用户看到的完整结果。
