# 安卓 release 构建与真机冒烟

安卓版是端内形态（`docs/adr/0009-android-embedded-form.md`）：APK 内含行为核心、进程内本机服务与原生编译的 UI，会话、记忆与 Provider Key 只落在手机的 App 私有目录里。这份文档管三件事——签名怎么一次性建好、release 包怎么构建与自检、上真机要逐项过什么。

签名不是构建细节，而是数据安全的一部分：签名身份换过，系统就拒绝覆盖安装，唯一出路是卸载重装，而卸载会把私有目录里的会话与记忆全清掉。**没有云端可以捞回来，跨设备唯一通道是手动导出**（`.scratch/android-apk-spec.md` 实现决策第 5 条「数据＝App 私有目录＋手动导出」与改动面「签名」那条红线）。所以下面这些看起来啰嗦的步骤，都是在保护那台手机上唯一的原件。

## 一次性准备：自建 keystore 与离线备份

### 生成

在任一台装有 JDK 的机器上执行（参数与 `apps/qiyu_flutter/android/key.properties.example` 的注释、以及 `scripts/build-android-apk.ps1` 缺 keystore 时打印的补齐指引同源，改动请三处一起改；命令写成一整行，方便直接粘贴执行）：

```powershell
keytool -genkeypair -v -keystore qiyu-release.keystore -alias qiyu -keyalg RSA -keysize 4096 -validity 10950
```

这一把是**终身签名身份**，不是用完可以丢的一次性钥匙：`-validity 10950` 是 30 年，覆盖这款 App 的整个生命周期；`-keysize 4096` 比 2048 多花不了多少体积，却省掉日后被迫换钥匙的借口。DN 字段（姓名、组织、城市）随你填，但要稳定——它进证书，证书进每一个包。别名 `qiyu` 一旦定了就别再改：换别名或换口令都意味着签名身份变了，旧手机上的数据就只能靠事先导出。

口令这里有一个会咬人的格式差异，实测过：上面那条命令不带 `-storetype`，生成的是 **PKCS12**，而 PKCS12 不支持给单个密钥条目另设口令——`keytool` 会直接忽略 `-keypass`（交互式生成时密钥口令就取密钥库口令）。所以走缺省格式，`key.properties` 里的 `keyPassword` 必须与 `storePassword` 填**同一个值**；填成两个不同的，预检与解析一路正常，直到 `:app:packageRelease` 才抛 `Get Key failed: Given final block not properly padded`，看着像口令错了其实错在格式不认这条。想用两个不同口令，就显式加 `-storetype JKS`（JKS 仍可用于签名，只是 JDK 会提示它是自有格式）。两种都实测签出了包：同口令的 PKCS12、异口令的 JKS。

口令建议只用 ASCII 可打印字符。口令要在三个环节之间保持一致：`keytool` 从控制台读入、`scripts/build-android-apk.ps1` 按 UTF-8 预检 `key.properties`、Gradle 也按 UTF-8 解析同一个文件（两侧都显式指定了 UTF-8，就是为了不出现「脚本预检通过、签名时口令却不是同一个」）。非 ASCII 字符要跨过整条链路都不变形并不显然，而口令变一个字节就等于换一次签名身份——用 ASCII 可以直接绕开这一类坑。

keystore 放哪儿都行，构建时把路径写进 `key.properties`；建议直接放 `apps/qiyu_flutter/android/`，那里已经被 `.gitignore` 用 `**/*.keystore`、`**/*.jks`、`key.properties` 三条盖住，`key.properties` 与 keystore 都进不了仓库。

### 填 key.properties

复制 `apps/qiyu_flutter/android/key.properties.example` 为同目录下的 `key.properties`，填四项：

```
storeFile=qiyu-release.keystore
storePassword=…
keyAlias=qiyu
keyPassword=…
```

`storeFile` 写绝对路径，或写按 `apps/qiyu_flutter/android/` 解析的相对路径。绝对路径要写成 `D:/keys/qiyu.keystore` 或 `D:\\keys\\qiyu.keystore`：这个文件按 Java Properties 格式解析，值里的单个 `\` 是转义符会被 gradle 吃掉，而脚本预检按原文取路径，写单反斜杠就会「预检通过、签名时报找不到 keystore」。这个文件要**以 UTF-8 保存**：脚本预检与 Gradle 解析都显式按 UTF-8 读它，用记事本「另存为 ANSI」存过就会两侧读出不同的值（同样是预检过了、签名时对不上）。**任何口令都不入库、不写进文档、不发到聊天工具里。**

### 离线备份

keystore 文件本体和两个口令必须分开存放：keystore 拷到一份加密移动硬盘或离线存储，口令记在密码管理器或写在纸上，两者不在同一个地方。备份介质不能上云，也不能放进任何会被同步的目录（网盘客户端的同步文件夹、随手 commit 的配置备份都算）——那等于把「数据只在我手机上」这条红线从签名侧捅破。

备份的验收只有一条：换一台机器、或本机盘挂了之后，单凭那份离线 keystore 加口令，能重新签出一个可以被旧手机覆盖安装的包。做不到的话，票面上这个「已备份」是假的。

别指望系统帮你留后手：`apps/qiyu_flutter/android/app/src/main/AndroidManifest.xml` 上 `allowBackup="false"`（票05 评审时关掉），云备份、设备到设备迁移与 adb 备份都拿不到私有目录——数据想出手机，只有 App 内导出这一条路。

### 证书指纹与离线备份：分发放行门槛

下面三件事没齐之前，**不要产出任何分发给别人的包**——临时钥匙可以用来验证构建链路，但产物当场删掉，别留下一个看着能分发的包：

1. 自建了那把终身 keystore（不是临时生成、用完就扔的那种）；
2. 它的证书 SHA-256 指纹记进了下面这张表；
3. keystore 本体离线备份完成，且与口令分开存放。

| 门槛项 | 值 / 状态 |
| --- | --- |
| 终身 keystore 已自建（路径与别名） | 待填（`key.properties` 的 `storeFile` 指向的就是它） |
| 证书 SHA-256 指纹 | 待填（按下面两种办法之一取，别抄第三方转述） |
| keystore 备份位置与日期 | 待填（介质与口令不在一起） |

指纹怎么取，两条路都实测过：

```powershell
# 一、构建脚本末尾直接打印（apksigner verify --print-certs 的输出）
& .\scripts\build-android-apk.ps1

# 二、不构建也能取：读 key.properties 里 storeFile 指向的那个 keystore
keytool -list -v -keystore <storeFile 指向的路径>   # 提示输入口令时再输入，口令不进命令行
```

两种输出是**同一个值的不同写法**：`apksigner` 打的是 `SHA-256 digest: <64 位小写十六进制、无分隔>`，`keytool -list -v` 打的是 `SHA256:  <大写、冒号分隔>`。比对前先去掉冒号并统一大小写，别按字符串直接相等就判定不一致。表里记 `apksigner` 那一条即可，因为分发前要比对的包通常就是脚本打出来的。

票09 验证构建链路时用过一把用完即删的临时钥匙（它不是本项目的签名身份，也没有离线备份），它的指纹不写进这张表。

## 日常构建

```powershell
& .\scripts\build-android-apk.ps1
```

脚本按顺序做四件事：预检 `android/key.properties` 存在、四个字段非空、`storeFile` 指向的 keystore 真的在；跑 `flutter build apk --release`；打印 APK 绝对路径、版本与大小；用 Android SDK build-tools 里最新版本的 `apksigner verify --print-certs` 打印签名证书指纹。找不到 `apksigner` 时不失败，只提示改用 Android Studio 的 APK Analyzer 或按上一节用 `keytool -list -v` 直接读 keystore 核对签名。

预检任一条不过，脚本打印一段中文指引（缺哪一项、怎么自建 keystore 与填 `key.properties`、备份怎么放）后以 exit code 1 退出，不会开始构建。

### 为什么不退回调试签名

`apps/qiyu_flutter/android/app/build.gradle.kts` 里对 release 签名做硬校验：`android/key.properties` 不存在、四个字段里任一项缺失或为空、`storeFile` 指向的 keystore 不存在，都会抛 `GradleException`，并且**一次把所有问题列全**（不用一轮补一个字段），消息里直接写明「宁可不构建也不退回调试签名」。

判定「这次是不是真要产出 release」用的是本次请求的任务名，按 Gradle 的驼峰缩写语义匹配（`assembleRelease`、`bundleRelease`、`packageRelease`、`validateSigningRelease`、`lintVitalRelease`、`installRelease`，以及会连带拉起 release 变体的 `assemble` / `build`；`check` 一族有意不列——它们只跑检查类任务、不产出需要签名的包，列进来会让没配 keystore 的机器连 `gradlew check` 都硬失败），所以 `./gradlew aR`、`./gradlew assembleR`、`./gradlew build` 这类缩写姿势同样会被拦下，不会只剩一句英文 AGP 报错。校验只在真正要产出 release 时生效，所以没有 keystore 的机器照旧能跑调试包：

```powershell
cd apps\qiyu_flutter
flutter build apk --debug      # 调试签名，不需要 keystore
flutter build apk --release    # 缺 key.properties 即失败
```

这条区分是有意留的：日常改 UI、试链路用 `--debug`，只有准备给人装的包才走 release 签名。**release 包请固定走 `scripts/build-android-apk.ps1` 或 `flutter build apk --release`**——理由不是怕签名校验被绕过，而是脚本会把预检、版本、大小与证书指纹一次打全，手敲 gradle 只有构建输出。

校验也绕不过去：实测留着「配好钥匙时存下的配置缓存」，再把 `key.properties` 与 keystore 删掉重跑 `./gradlew :app:assembleRelease`，Gradle 判定缓存失效、重新配置，上面那条中文校验照样生效（配置期读过的文件是缓存的输入）。即便真走到 AGP 自己的检查，签名配置不完整时它是失败或产出未签名包，**不会**静默改用调试钥匙——红线不破。

产物路径固定为 `apps/qiyu_flutter/build/app/outputs/flutter-apk/app-release.apk`（`--debug` 对应同目录的 `app-debug.apk`）。

### 构建耗时与附带检查

release 构建会顺带跑安卓 lint 致命检查（任务图里含 `:app:lintVitalAnalyzeRelease`、`:app:lintVitalRelease`），这两步不过发包就出不来，所以脚本 exit 0 就等于它们过了；要单独核验，跑 `cd apps\qiyu_flutter\android; .\gradlew :app:lintVitalRelease --rerun`，以退出码为准（票09 交付那次记下的 `No issues found` 文字随临时产物一起删了，已无从复核，不再当凭据）。

产物大小与版本每次由脚本打印（`==> release APK: <绝对路径>` 与 `==> 版本 X(Y)，大小 Z.ZZ MB` 两行），照抄即可：票09 修复复核时重跑脚本得 69.50 MB、版本 0.1.0（versionCode 1）。

第一次跑 release 会明显很慢：要下载 release 侧依赖，还要用 NDK/CMake 编四条 ABI，实测跨多次尝试约 25 分钟。缓存热了就快得多：`flutter build apk --release` 一条实测 7.7 秒到 35.1 秒（差异在 flutter 侧资源打包与 lint 是否命中缓存），纯 gradle 重复跑 `./gradlew :app:assembleRelease` 多数任务 up-to-date，实测 3 秒。看到长时间没有输出不要判定为卡死去中断它。

`apps/qiyu_flutter/android/gradle.properties` 里 `kotlin.incremental=false` 是有意关掉的：Kotlin 2.3.20 的 Build Tools API 在 Windows 上会把增量缓存重复注册（`already registered` / `Could not close incremental caches`），让插件模块的 `compileDebugKotlin` 随机失败。排查安卓编译报错时先别动这一行，注释自记为「ticket 07 实测，产物不受影响」。

### 分发前自检

这是放行门槛，不是事后补记录：「证书指纹与离线备份：分发放行门槛」那节表里三项（自建终身 keystore、指纹已抄进表、离线备份完成且与口令分开存放）任一条没落地，就**不分发**——包留在本机、装进自己手机试可以，别交给任何人。

三条都齐后，再把脚本打印的 SHA-256 指纹与表里那条比对（两种写法要先归一化：去掉冒号、统一大小写），逐字符一致才发出去。不一致意味着签名身份已经变了——这个包装不上旧手机上的数据，旧数据也换不回来。发之前先停下来查是哪一步走错（拿错 keystore、`storeFile` 指到别的文件、还是口令填串了），别先发给别人。

### CI 不跑安卓构建

既定决策，见 `.scratch/android-apk-spec.md` 实现决策第 8 条：CI 时长与现状相当，安卓由本地脚本加真机冒烟清单兜底。核对过现状——`.github/workflows/ci.yml` 里与安卓相关的构建一步都没有（Flutter job 只跑 `flutter build web --wasm --no-web-resources-cdn`），`scripts/verify-release-baseline.ps1` 也不含安卓步骤，它跑的是四包分析/测试、Web 构建与 Windows 打包验收。也就是说：交付门禁全绿不代表 release APK 能构建出来，安卓那一头只有本文件和下面的清单在守。

## 版本与覆盖升级

版本号只有一处：`apps/qiyu_flutter/pubspec.yaml` 的 `version: 0.1.0+1`。`+` 前是 versionName（用户看得见），`+` 后是 versionCode（系统判断能不能覆盖安装），Flutter 把这两个值喂给 Gradle，`android/app/build.gradle.kts` 里 `versionCode = flutter.versionCode` / `versionName = flutter.versionName` 直接取用。不要在 gradle 里另写一份。

覆盖安装要求两件事同时成立：versionCode 严格递增，签名证书与已装的完全一致。任一条不满足，系统拒装（常见的报法是 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` 或「与已安装应用签名不同」），而不是静默替换。

**遇到签名不匹配或降级安装被拒，正确处置是先在 App 里导出备份，再卸载重装。**不要直接卸载——卸载即清空私有目录，那一刻你手上还没有任何原件的副本。

升级本身要验的数据不丢，做法是本地演一遍：

1. 装上 v1，制造一点只有本机才有的东西：聊几轮、说晚安、在设置里填好 Provider 与 Key、把朗读音量拖到某个非默认值、（若配了语音）记一下代理地址。
2. 只改 `pubspec.yaml` 的 version（例如 `0.1.0+1` → `0.1.1+2`），重新构建。
3. 装机时选择覆盖安装，不卸载。
4. 打开后逐条对上：会话与记忆还在（聊天页能滚到旧内容、历史按日可看、记忆中心读得出来）；设置页 Provider 配置原样、Key 仍不回显明文；朗读音量与静音状态保持你上次拖的位置。

任何一项没了，就不是「升级流程小问题」，而是签名或数据目录出了错，先查清再发版。

## 真机冒烟清单

需要一台安卓真机和一个配好的豆包 Key，全部条目由本人上机执行。用 release 包跑（网络配置、签名、lint 走的是真实路径，`--debug` 过不能代替它）；每项写「怎么做 → 看到什么算通过」，不过就停下记现象，别顺手改代码把现象盖掉。

票01 与票03 各留了一条「待真机」，指的是 PC 上浏览器的人工操作，与手机无关，不进本清单；本清单收的是票04–08 登记的 11 条真机待用户项，加上票06 附项里点名「登记进 09」的三条，按一次连续上机的操作顺序重排。

- [ ] 1 安装与首启。`flutter install --release` 或直接把 APK 传到手机打开；系统提示「未知来源」时允许本应用安装。看到：安装成功，桌面出现「栖语」图标，点开进入初见页（问怎么称呼你那一屏），整个过程没有白屏、没有弹出任何连不上服务的报错。
- [ ] 2 初见引导落到合一页。按引导继续，选「开始聊天」或「先去连上模型」都走一遍（后者看完设置页再回聊天）。看到：引导完成后进聊天页空态，问候位正常，导航收在抽屉里，字阶是移动档、正文不横向溢出。
- [ ] 3 配 Key 且不回显、重启仍在。抽屉 → 设置 → 模型连接，选豆包，填 API Key 保存，再做一次连接测试。看到：测试给出可读的成功结果；凭据块标题变成「API Key 已保存在本机 provider.json」并带「留空即可继续使用；输入新值会覆盖旧值…」这句说明，输入框与任何返回信息里都不出现明文 Key；杀进程重开后仍是这个状态，聊天真能把豆包调通（票05 的真机项）。顺手确认「忘记已保存的 Key」的确认框写的是「忘记后本机不再保存这个 Key…」。
- [ ] 4 流式聊天。回聊天页发一句「今天有点累」。看到：回复逐句出现而不是整段憋出来；结束后这条回复作为完整一轮留在屏上；期间切到后台再切回来，回复不错乱、不重复、不丢（故事 6）。
- [ ] 5 停止生成。再发一句会引出较长回复的话，生成中点发送位上的停止钮（tooltip 为「停止回复」）。看到：文本立刻停止增长，已可见的部分作为一轮留下，不出现继续往外冒字、也不出现空的半截气泡。
- [ ] 6 晚安与日终归档。说一句「晚安」。看到：回复是结合当天语境的收束，不是固定套话；随后在记忆中心能看到当天的归档（「当天小结」一类条目），历史页能看到那一段会话。这一步之后不要再动手机，让后台节奏跑完。
- [ ] 7 杀进程与重启手机幂等。两档都要做：先从最近任务里划掉 App 再重开；然后重启一次整机（不是只划 App），开机后直接打开栖语。看到：两档之后聊天页都恢复最近的会话内容，没有哪句话重复出现两遍；历史里同一条消息也只有一份（requestId 幂等）。重启这一档还要验「未闭环事项原样恢复」：如果昨晚说晚安后日终归档或 Dream 还没跑完就重启了，打开 App 等它空闲一会儿，欠下的归档要补上、记忆中心读得到，既没丢也没重复（跨好几天的补扫是第 8 项，这里只管整机重启这一档；两档之间不需要再制造新数据）。
- [ ] 8 启动补扫与 Dream 补办。把手机放着隔两三天（或改系统日期跨过间隔），期间不打开 App；再启动并等它空闲一会儿。看到：欠下的日终归档被补上、记忆中心补齐那几天的记录；满足最小间隔时 Dream 也补做，长期印象层有更新。补做过程中打开聊天不卡、不被后台任务挡住房间（不阻塞首个回应）。

## 已知待裁与未核实

- 清单第 3 项的判据按**现行实现**写：Provider Key 主存本机 `provider.json`，凭据仓（安卓 Keystore / Windows 凭据管理器）只做迁移回退与旧值清理。总规格里有两处文字与它冲突：用户故事 17「Provider Key 存在系统级安全存储、设置页永不回显明文」，以及实现决策第 4 条「凭据＝Android 系统安全存储（Keystore 支撑）」。这处出入由票05 评审暴露、卡内记为「架构出入待裁定」，其后（2026-09-09）的裁定是 Key 主存保持 `provider.json`（PC 与安卓同构）、不另开票迁入安全存储，但上述两处规格文字尚未同步。上机时按本清单判，不要因为故事 17 把这条判成不通过；规格文字与实现谁向谁收口属产品裁定范围，本票未擅自改动。
- 隐私与设置页原有的两处 PC 口径文案已订正为设备中性说法：`apps/qiyu_flutter/lib/features/settings/privacy_view.dart` 的分节标题现为「数据只保存在你自己的设备上」，`apps/qiyu_flutter/lib/features/settings/provider_settings_view.dart` 本地数据节现为「全部会话与记忆都是这台设备上的 Markdown 文件」。第 3、23 项按订正后的文字核对。
- 聊天页麦克风置灰引导里「当前浏览器不支持语音输入，请换 Chrome 或 Edge。」（`apps/qiyu_flutter/lib/features/chat/qiyu_composer.dart`）在安卓上走不到：`IoVoiceRecorderPlatform.supported` 在安卓恒为真，机型采集失败是按第 13/14 项的「无法使用麦克风」口径报。这条仅作为浏览器侧文案存在，不影响本清单。
- 返回键在产品规格里是用户故事 4（「按系统返回键时行为符合直觉：回上一界面或确认退出」），但九票拆分时没有一张票承接它，聊天页根路由也没挂任何 `PopScope`。它到底算不算已满足，只能由第 21 项的真机现象定；实测不接受就该另开票，不要就地改导航行为来凑。
- 票09 验收项要求「verify-release-baseline 全量门禁绿」，本文件核对的是当前脚本内容：它不含任何安卓构建步骤。因此门禁绿只证明 PC 四包未被安卓化拖累，release APK 的可构建性由上面的构建实测与本清单负责。
- 第 14 项（机型不支持 16kHz）与第 15 项（来电/耳机拔出）取决于手上机型，若无法构造就记「未覆盖」并说明原因，不要写「应该没问题」。
- 冷构建总耗时受缓存与网络影响，「约 25 分钟」是票09 交付那几次尝试的跨度，不是契约数字。
